# Contributing to HiveMind

Thank you for your interest in contributing to HiveMind! HiveMind is an open-source, read-only incident investigation and remediation proposal tool for Kubernetes.

---

## 1. Safety Invariant

HiveMind is strictly **read-only and non-mutating**:
- Never add features that mutate live Kubernetes cluster state.
- Never add direct cluster clients (`kubernetes`, `pykube`, etc.) or cloud provider SDKs.
- Proposals generated by HiveMind carry an immutable `status: "NOT_APPLIED"`.
- All user inputs and Kubernetes manifests are treated as untrusted.

---

## 2. Prerequisites

- **Python**: 3.11 or higher
- **Git**

### Development Installation

Clone the repository and install HiveMind with development dependencies:

```bash
git clone https://github.com/hivemind/hivemind.git
cd hivemind
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

---

## 3. Code Quality & Standards

All code contributions must meet strict formatting, linting, and type checking standards before submission.

### Code Style & Linting

HiveMind uses [Ruff](https://github.com/astral-sh/ruff) for linting and code formatting:

```bash
# Check code style and formatting
python -m ruff check src/ tests/

# Automatically fix format and import sorting issues
python -m ruff check --fix src/ tests/
```

### Static Type Checking

HiveMind enforces strict typing using [mypy](https://mypy-lang.org/):

```bash
python -m mypy src/
```

All functions and methods must contain type annotations. Do not use untyped functions (`disallow_untyped_defs = true`).

### Testing

Run the full test suite with pytest:

```bash
# Run all tests
python -m pytest tests/ -v

# Run with test coverage
python -m pytest --cov=hivemind --cov-report=term-missing tests/
```

All existing and new tests must pass unequivocally. Never lower test coverage.

## 4. Commit Message Conventions

HiveMind strictly follows the [Conventional Commits](https://www.conventionalcommits.org/) specification:

Format:
```
<type>(<scope>): <short description>
```

Common types:
- `feat`: A new feature (e.g., `feat(cli): add batch analysis command`)
- `fix`: A bug fix or security patch (e.g., `fix(audit): add hostPath guardrail`)
- `refactor`: Code reorganization without functional changes (e.g., `refactor(proposal): split into focused modules`)
- `docs`: Documentation updates or additions (e.g., `docs: add troubleshooting runbook`)
- `test`: Adding or improving tests (e.g., `test(k8s): add memory parsing edge cases`)
- `chore`: Maintenance tasks, dependencies, or tool configs

---

## 5. Pull Request Process & CI Expectations

1. **Create a Topic Branch**:
   ```bash
   git checkout -b feat/your-feature-name
   ```
2. **Implement Changes & Tests**:
   - Write tests for all new behavior and edge cases.
   - Maintain documentation integrity; preserve existing docstrings and comments.
3. **Verify Locally**:
   ```bash
   python -m ruff check src/ tests/
   python -m mypy src/
   python -m pytest tests/ -v
   ```
4. **Submit Pull Request**:
   - Provide a clear PR description detailing what was changed and why.
   - Reference any relevant issues.
   - Confirm all CI checks pass.
